## Findings

### Finding 1: Sandbox escape via `str.format()` attribute-chain traversal bypasses dunder blocklist — `minichain/contract.py:283-311`

- Severity: Critical
- Confidence: 0.85
- Category: sandbox_escape
- Description: `_validate_code_ast` (contract.py:283-311) rejects `ast.Attribute`/`ast.Name` nodes starting with `__`, string *literals* containing `__`, f-strings, and direct calls to `type`/`getattr`/`setattr`/`delattr`. It does not reject `ast.Add` (string concatenation) or `ast.Mod`, and it only blocks calls whose `func` is a bare `ast.Name` — a method call like `x.format(...)` has `func` as an `ast.Attribute`, which is never checked. Because dunder names can be assembled at runtime from short literal fragments (e.g. `"_" + "_globals" + "_" + "_"` → `"__globals__"`), none of which individually contains `"__"`, the AST validator never sees the resulting string. That runtime string can then be used as a `str.format()` template. Python's format-spec mini-language supports chained attribute (`.`) and item (`[key]`) access entirely inside the format string, parsed by `str.format` itself — not by `ast.parse` — so this traversal is completely invisible to the validator.
- Exploit Scenario: A deployed contract builds `"{0.__globals__[sys].modules[os].environ}"` one `+`-joined fragment at a time (so no literal ever contains `__`), then calls `.format(transfer_out)` (or `call_contract`), both of which are real Python function objects injected into the sandbox's builtins at contract.py:86 and contract.py:95, each carrying a normal `__globals__` (the module-level namespace of `contract.py`, which includes `sys`, `json`, `logging`, `multiprocessing`). Since `multiprocessing.Process` defaults to `fork` on Linux, the worker subprocess is a full copy-on-write fork of the node process, so `sys.modules` inside it contains every module the node has loaded — not just what `contract.py` imports directly. Walking `__globals__[sys].modules[...]` this way lets contract code read and exfiltrate (via the stringified result returned to the caller/storage) process-wide state such as environment variables, and potentially other in-memory secrets (e.g. node signing keys) held by any already-imported module, depending on deployment. The format-spec grammar has no call syntax, so this specific primitive is read-only introspection/exfiltration rather than direct code execution, but it fully defeats the sandbox's stated purpose of blocking "sandbox escape via introspection."
- Recommendation: Do not allow untrusted code to call `.format()` (or `%`-style formatting, or f-strings — already blocked) on arbitrary objects. Either remove `str` from the allowed builtins and provide a safe, allowlisted string-building helper instead, or block all `ast.Attribute` calls whose `attr` is `format` (and other dunder-adjacent formatting hooks), and additionally reject `ast.BinOp` with `ast.Add`/`ast.Mod` between string literals used to reconstruct blocked substrings — but the more robust fix is to stop relying on blocklisting dangerous *syntax* and instead run contract code with builtins that have no path back to `__globals__`/`__class__` at all (e.g. execute with a `str` subclass or wrapper type that lacks `.format`, or strip `format`/`__format__` support from injected callables via a proxy object instead of passing raw function objects into the sandboxed builtins).
